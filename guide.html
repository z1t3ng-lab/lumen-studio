The evidence comes first.

REA opened Adobe's public Make colors pop sample without an account, changed Exposure from 0 to +1.00, and captured the result. The photo brightened, the histogram shifted, and Save became enabled.

Captured code includes named adjustment parameters, state updates, a rendering bridge, WebGL display initialization, and Canvas preview paths. That supports the architectural explanation below; it does not reveal the complete rendering algorithm.

What is proven? A real interaction and inspectable client-code boundaries. What remains unknown? Adobe's exact tone equations, RAW processing, authenticated saving/export, and equivalence with the desktop application. Static analysis has partial coverage. Read the full finding ledger.

Build the editing loop.

These are the actual stages implemented in Lumen. The controls and algorithms are our own.

Original photograph＋Edit recipe→Pixel worker→Preview / export
01

Keep the original.

Import a JPEG, PNG or WebP. Store its bytes as a Blob and keep adjustments in a separate recipe. The photo stays reversible because sliders change the recipe, not the original file.

Inspect storage.js and engine.js.
See a simplified recipe
{
  "exposure": 0.5,
  "highlights": -20,
  "temperature": 12,
  "rotation": 0,
  "crop": null
}
02

Render light, then color.

Decode a preview up to 1600 pixels on its long edge. Convert sRGB to linear light, apply exposure and color gains, then tonal weights. Return to display RGB for contrast, saturation, vibrance, vignette and sharpening.

Exposure uses linear × 2^EV. In our tested neutral patch, an encoded channel value of 80 becomes 111 at +1 EV. This verifies our implementation; it is not a claim about Adobe's complete formula.

Inspect the pixel pipeline and numerical tests.
03

Let the interface stay responsive.

A Web Worker processes pixels away from the interface thread. The editor tags each render request and discards stale results, so a slow render cannot replace a newer edit or another photograph.

Inspect worker.js and the editing controller.
04

Add crop, history and looks.

Crop stores a normalized rectangle in the rotated image. Undo and redo restore recipe snapshots. A preset is a collection of ordinary slider values. Before/after returns to preserved original pixels.

Try Crop → 1:1 → Apply crop, or draw a freeform rectangle. Use ⌘/Ctrl Z to undo, ⇧⌘/Ctrl Z to redo, and B to compare.

Inspect geometry, history and preset interactions.
05

Export from the full original.

Export decodes the stored original at full resolution and applies the same recipe. It then rotates, crops, optionally resizes, and encodes a new JPEG or PNG. A photo wider than the preview still exports at its original dimensions.

PNG preserves transparency; JPEG places white behind transparent pixels. Both produce 8-bit RGB output and omit camera metadata.

Verified by decoded downloaded files in browser test results.
06

Prove the behavior.

Twenty-three engine tests cover the pixel pipeline, curves, selective color, masks, filtering, retouching, optics and grain. Sixty browser, desktop and geometry checks exercise the controls, downloads, persistence, coordinate alignment, keyboard interaction, mobile layout and error recovery.

A SHA-256 check confirms that editing, exporting and reopening the library leave the stored original bytes unchanged. Tests observed no external application requests while editing.

07

Use it on your own photographs.

  1. Open the editor and import photos or try the included sample.
  2. Adjust Light and Color, or choose a look on the wider desktop layout.
  3. Crop, compare, and undo until the result feels right.
  4. Export a new JPEG or PNG. Save a JSON edit recipe on desktop if you want to reapply it.
